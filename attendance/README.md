# Wi-Fi Attendance — учёт прихода/ухода по рабочему Wi-Fi

Учёт присутствия сотрудников по факту подключения их личного/рабочего
телефона к корпоративной Wi-Fi сети (роутер Xiaomi AX3000T / RD23).
Полное ТЗ обсуждалось в чате — см. историю разработки; здесь только то, что
нужно для эксплуатации и продолжения работы.

**Статус:** код написан и покрыт тестами на всех сценариях из ТЗ (раздел 33),
веб-панель проверена вручную (curl) с тестовым `fake`-адаптером. **Реальный
роутер ещё не подключался и не проверялся** — см. раздел
["Когда появится доступ к роутеру"](#когда-появится-доступ-к-роутеру) ниже,
это первое, что нужно сделать на месте.

## Быстрый старт (локально, без роутера)

```bash
cd attendance
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# сгенерировать SECRET_KEY:
python -c "import secrets; print(secrets.token_hex(32))"
# вписать его и свой ADMIN_PASSWORD в .env — ROUTER_ADAPTER=fake можно не трогать

uvicorn attendance.main:app --reload --host 127.0.0.1 --port 8000
```

Открыть `http://127.0.0.1:8000`, войти под `ADMIN_USERNAME`/`ADMIN_PASSWORD`
из `.env`. С `ROUTER_ADAPTER=fake` устройства в сети всегда пустые — это
нормально, весь остальной функционал (сотрудники, привязка устройств вручную,
история, настройки) работает и без роутера.

Тесты:

```bash
pip install -r requirements-dev.txt
pytest
```

## Когда появится доступ к роутеру

Порядок действий, чтобы быстро всё донастроить и проверить на месте:

1. **Убедиться, что роутер доступен по сети** с машины, где будет крутиться
   сервис: `curl -v http://192.168.31.1` (или актуальный IP роутера).

2. **Прогнать CLI-проверку логина и списка устройств**, не поднимая веб-панель:

   ```bash
   cd attendance
   source venv/bin/activate
   python -m attendance.tools.test_router_connection \
       --url http://192.168.31.1 --username admin --password '<реальный пароль>'
   ```

   Ожидаемо: список устройств в формате `{"mac": ..., "hostname": ..., "ip": ...}`.

   **Если скрипт падает с ошибкой** — почти наверняка дело в
   `attendance/router_adapter/xiaomi.py`: схема логина MiWiFi (nonce +
   хеширование пароля) и формат ответа `misystem/devicelist` взяты из
   общеизвестных reverse-engineering схем, не из официальной документации, и
   могут отличаться на вашей конкретной прошивке RD23. В файле явно
   помечено, что именно может отличаться (см. комментарий в начале файла) —
   правится только этот файл, остальной сервис (БД, веб-панель, логика
   таймаутов) от деталей API роутера не зависит благодаря интерфейсу
   `RouterAdapter`. Частые причины ошибки:
   - `code` в ответе логина не `0` → пароль/логин не подошли, либо не тот
     алгоритм хеширования (`_build_password_hash` в `xiaomi.py`);
   - нет `stok`/`token` в ответе → поле называется иначе, посмотреть сырой
     JSON (скрипт печатает текст ошибки с обрезанным телом ответа);
   - нет `list` в ответе devicelist → либо другой путь API, либо нужна
     дополнительная авторизация уровня "gateway".

3. **Проверить рандомизацию MAC на реальных телефонах сотрудников** — самое
   важное практическое действие. Логика:
   - Подключить тестовый телефон к рабочей сети.
   - Прогнать `test_router_connection.py` ещё раз, найти телефон в списке —
     это и есть MAC, который реально видит роутер (может отличаться от MAC,
     подписанного на коробке телефона, из-за privacy-адреса per-SSID — это
     нормально и ожидаемо).
   - **Отключиться от сети и подключиться заново** («забыть сеть» и
     подключиться снова) — проверить, что MAC остался тем же. Если
     изменился — на этом телефоне включена периодическая ротация
     приватного MAC, и его придётся либо донастроить (см. п.5), либо
     полагаться только на эвристику авто-подсказки (п.6 ниже).
   - Held test: выключить Wi-Fi на телефоне на 25+ минут, снова включить —
     сотрудник должен корректно уйти и прийти заново (это уже проверено
     тестами на fake-адаптере, но стоит перепроверить с реальным роутером
     хотя бы раз, т.к. таймаут закрытия зависит от того, насколько быстро
     сам роутер убирает "уснувшее" устройство из своего списка клиентов —
     см. п.4).

4. **Откалибровать `ABSENCE_TIMEOUT_MINUTES`**, если нужно. 20 минут — значение
   по ТЗ, но конкретный роутер может держать неактивное устройство в списке
   клиентов дольше/меньше, чем реальное время его физического отсутствия
   (ARP-таймауты, keep-alive). Меняется в `/settings` без перезапуска.

5. **(Опционально) отключить приватный MAC-адрес на телефонах сотрудников**
   для сети офиса — обсуждали отдельно: это разовая настройка при выдаче
   доступа к Wi-Fi, а не постоянное требование к сотрудникам. iOS: настройки
   сети → "Приватный адрес Wi-Fi" → выключить (для этой сети). Android:
   настройки сети → приватность → "Использовать MAC устройства". Без этого
   шага система тоже будет работать (MAC берётся "по факту" при регистрации,
   см. `/employees/{id}/device`), но смена MAC станет чуть более вероятной.

6. **Переключить адаптер на боевой** в `/settings` (или сразу в `.env` для
   первого деплоя): `ROUTER_ADAPTER=xiaomi`, вписать `ROUTER_BASE_URL`,
   `ROUTER_USERNAME`, `ROUTER_PASSWORD`. На странице настроек есть кнопка
   **«Проверить соединение»** — она пробует введённые (ещё не сохранённые)
   параметры прямо там же, без похода в консоль.

7. **Прогнать полный сценарий приёмки** — ТЗ раздел 37 / 33 (тесты 1-8):
   создать сотрудника → привязать реальный телефон через
   «Добавить устройство» (выбор из списка, обнаруженного роутером) →
   прийти в офис → проверить "🟢 На работе" → выключить Wi-Fi на 5 минут →
   убедиться, что статус не изменился → выключить на 25+ минут → дождаться
   "🔴 Ушёл" → снова включить → убедиться, что создалась новая сессия →
   выключить сам роутер на несколько минут → убедиться, что показывается
   баннер "⚠️ Нет связи с роутером" на дашборде и никто не помечен ушедшим
   автоматически.

## Архитектура

```
Xiaomi AX3000T (или fake для разработки)
        │  RouterAdapter.get_connected_devices()
        ▼
router_adapter/  (xiaomi.py, fake.py — реализации; base.py — интерфейс)
        │
        ▼
services/monitor.py   — фоновый цикл, раз в POLL_INTERVAL_SECONDS
        │
        ▼
services/attendance.py — ядро: приход/уход/таймаут/защита от сбоя роутера
        │
        ▼
database/repository.py → SQLite (employees, devices, attendance_sessions,
                          system_events, app_settings, admin_users)
        │
        ▼
web/  (FastAPI-роуты + Jinja2-шаблоны)  →  https://work.noir-ekb.com
```

Router Adapter намеренно изолирован интерфейсом `RouterAdapter`
(`router_adapter/base.py`) — чтобы заменить Xiaomi на другой роутер в
будущем, не трогая ничего в `services/` или `web/`. `FakeRouterAdapter`
используется для разработки/тестов и переключается в `/settings` без
единой правки кода.

### Ключевое архитектурное решение: различение "не увидели устройство" vs "не получили список"

`RouterAdapter.get_connected_devices()` обязан возвращать
`RouterPollResult(success=False, ...)`, а не бросать исключение, при любой
проблеме — это единственное, что позволяет `services/attendance.py`
корректно не помечать всех сотрудников ушедшими при сбое связи с роутером
(ТЗ разделы 13, 32 — принципиальное требование). См. тест
`test_router_failure_does_not_close_active_session`.

### Настройки: .env vs БД

`.env` задаёт значения только для **первого запуска** (`SECRET_KEY`,
`ADMIN_USERNAME`/`ADMIN_PASSWORD` — учётка админа веб-панели создаётся один
раз при пустой таблице `admin_users`). Интервал опроса, таймаут отсутствия,
адрес/логин/пароль роутера и часовой пояс живут в таблице `app_settings` и
редактируются на странице `/settings` без передеплоя — `.env` для них лишь
"начальное значение по умолчанию", если в БД ещё ничего нет.

### Эвристика "возможно, сменился MAC"

Обсуждали отдельно проблему рандомизации MAC-адресов на современных
телефонах. Решение в `services/attendance._check_possible_device_changes`:
если зарегистрированный телефон не виден дольше `LONG_ABSENCE_HINT_HOURS`
(по умолчанию 3 часа), а в сети появляется незарегистрированное устройство с
тем же hostname, что раньше отдавал этот телефон — в `/logs` и на дашборде
появляется подсказка для администратора с предложением перепривязать
устройство. Это не автоматическая подмена (риск ошибиться), а быстрая
ручная переассоциация в 1-2 клика через карточку сотрудника.

## Деплой (VPS, Supervisor)

Конвенция репозитория — все боты/сервисы на VPS `root@77.110.125.73` живут в
`/root/<имя>` и запускаются через Supervisor (см. корневой `CLAUDE.md`), не
systemd.

```bash
# на сервере
git clone <repo> /root/work-attendance   # или скопировать актуальный код
cd /root/work-attendance/attendance
python3 -m venv venv
venv/bin/pip install -r requirements.txt
cp .env.example .env
# заполнить .env: SECRET_KEY, ADMIN_PASSWORD, ROUTER_* (см. чек-лист выше)

cp deploy/supervisor/work-attendance.conf /etc/supervisor/conf.d/
supervisorctl reread && supervisorctl update
supervisorctl start work-attendance
supervisorctl status work-attendance

cp deploy/nginx/work-attendance.conf /etc/nginx/sites-available/
ln -s /etc/nginx/sites-available/work-attendance.conf /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
certbot --nginx -d work.noir-ekb.com   # HTTPS, допишет редирект 80->443 сам
```

Логи: `/var/log/work-attendance.out.log` и `.err.log`.

Обновление после изменений в коде:
```bash
cd /root/work-attendance && git pull
attendance/venv/bin/pip install -r attendance/requirements.txt
supervisorctl restart work-attendance
```

## Что сознательно не сделано (не входит в MVP, см. ТЗ раздел 35)

Telegram-уведомления, несколько устройств на сотрудника, несколько офисов/
роутеров, определение опозданий/раннего ухода, экспорт CSV/XLSX, роли
пользователей — см. ТЗ. Архитектура (отдельный `RouterAdapter`, `app_settings`
как расширяемая таблица настроек, `system_events` для диагностики) намеренно
оставляет место под всё это без переписывания ядра.
