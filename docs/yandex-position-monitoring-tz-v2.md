# ТЗ v2: система мониторинга позиций сайтов в выдаче Яндекса

> Версия 2. Уточняет исходное ТЗ по итогам ревью: стратегия сбора данных,
> определение позиции, метрики, схема БД, реалистичный масштаб и MVP.
> Разделы, не затронутые здесь, действуют по исходному ТЗ.

---

## 0. Что изменилось в v2 (сводка решений)

1. **Стратегия сбора — гибридная.** Непесонализированные профили собираем через
   **официальный Yandex Search API**, персонализированные — через браузерный
   скрейпинг с VPS + сервис распознавания капчи. Прокси — опциональный задел на
   рост, не требование MVP.
2. **Реалистичный масштаб.** Целевой сценарий проекта — ~30-40 запросов, 5-7
   сайтов. Единица работы — **выборка выдачи** (`запрос × профиль`), а не «проверка
   сайта». Сайты матчатся по уже скачанной выдаче без дополнительных запросов.
3. **Колдунщики пропускаем.** SEO-позиция считается по органической выдаче.
4. **Дубли домена** — берём лучшую (высшую) позицию, остальные вхождения игнорим.
5. **Локальные запросы** — дополнительно и отдельно трекаем позицию в блоке
   Яндекс.Бизнеса (не смешивая с органикой).
6. **Средняя позиция** — без учёта NULL, но всегда рядом с показателем coverage.
7. **Схема БД выпрямлена:** `check_runs` — единица работы, `checks` ссылается на
   `check_run_id`; добавлены `users`, `audit_log`; определены `notifications`,
   `reports`, `position_history`; `match_mode` у сайтов; шифрование cookies;
   ретеншен и партиционизация.
8. **MVP урезан** до одного профиля и ядрового цикла; аналитика и отчёты —
   следующими этапами. Перед полной разработкой — пилот.

## 1. Стратегия сбора данных (ключевой раздел v2)

Сбор выдачи Яндекса — главный технический риск проекта. Поэтому источник данных
выбирается **под каждый профиль отдельно**.

### 1.1. Официальный Yandex Search API — для непесонализированных профилей

Профили, которым не нужна живая персонализированная сессия, а достаточно
«регион + устройство», собираются через **официальный Yandex Search API**
(`yandex.ru/search/xml` / актуальный Search API). Плюсы: легально, стабильно,
**не отдаёт капчу**, не требует прокси.

Через API собираем профили:

- **Новый пользователь** (чистый, регион Екатеринбург);
- **Desktop** (регион + десктоп);
- **Mobile** (регион + мобайл).

Регион задаётся параметром `lr` (Екатеринбург = `54`), устройство — параметром
типа выдачи (desktop/mobile). Глубину задаём параметром числа результатов.

> Ограничение: API не воспроизводит персонализацию (cookies, история, состояние
> профиля). Для перечисленных профилей это допустимо — они и определяются как
> «регион + устройство без персонализации».

### 1.2. Браузерный скрейпинг (Playwright + Chromium) — для персонализированных профилей

Профили, которым нужна живая сессия с сохранённым состоянием, собираются
браузером с сохранёнными persistent-профилями:

- **Екатеринбуржец** (устоявшийся локальный профиль);
- **Приезжий** (исходный регион иной, местоположение — Екатеринбург).

Требования к браузерному сбору:

- Персистентное состояние браузера на профиль (cookies, storage) — как в
  исходном ТЗ.
- Регион дополнительно фиксируем параметром `lr=54`, а не только геолокацией.
- **Пейсинг:** рандомизированная пауза 15-40 с между выборками, отдельная пауза
  между страницами пагинации.
- **Капча:** при SmartCaptcha — решение через сервис распознавания
  (2captcha / rucaptcha / anti-captcha) как основной путь; при неудаче — статус
  `CAPTCHA`/`BLOCKED` и повтор позже, без записи позиции.
- Реалистичные UA/viewport под устройство.

### 1.3. Инфраструктура и прокси

- Всё крутится на существующем **VPS** (`magic-copper`). Отдельная прокси-ферма
  для целевого объёма **не требуется**.
- IP VPS — датацентровый, поэтому для браузерного сбора закладываем сервис
  распознавания капчи. Связка **VPS-IP + решалка капчи** — базовый вариант.
- **Резидентский прокси** (аренда) — опциональный запас на случай роста числа
  блокировок. **Мобильный прокси** — крайний резерв, в MVP не используется.

### 1.4. Слой-абстракция источника

Позиции и полная выдача должны сохраняться в **единой схеме независимо от
источника** (API или браузер). В коде — интерфейс `SearchProvider` с
реализациями `YandexApiProvider` и `BrowserProvider`; выбор провайдера — свойство
профиля. Поле `source` (`api` / `browser`) сохраняется в каждом прогоне для
аудита.

### 1.5. Режимы измерения: SEO (ночь) и Боевая выдача (день)

Проверка бывает двух типов (`run_mode`), с разной целью, ценой и источником:

**Режим `seo` — «чистая органика», ночью.**
- Источник: Yandex Search API, **отложенный ночной тариф** (25,41 ₽/1000) —
  самый дешёвый; персонализированные профили — браузер.
- Что меряем: **органическую позицию** (реклама и колдунщики исключены).
- Зачем: честная динамика SEO без шума рекламы; органика по часам стабильна,
  поэтому ночью снимать корректно и дёшево.

**Режим `battle` — «боевая выдача», днём/вечером.**
- Источник: **только браузерный сбор** — официальный API рекламу (Директ) не
  отдаёт, живую страницу с рекламой видит лишь браузер.
- Что меряем по той же выдаче, дополнительно к органической позиции:
  - `visual_position` — реальный номер твоего органического результата на
    странице, **считая все блоки над ним** (реклама, колдунщики). Показывает,
    насколько глубоко скроллит живой пользователь днём;
  - `ads_above` — сколько рекламных блоков (Директ) стоит над тобой.
- Зачем: как реально видит клиент днём, когда все, включая нас, бьются за места.

Оба режима пишут в общую историю; в аналитике органическая позиция (стабильная)
и боевая визуальная позиция показываются раздельно, чтобы техническую разницу
день/ночь не спутать с изменением SEO. Рекламные блоки сохраняются в полной
выдаче (`result_type=ad_top/ad_bottom`) при любом браузерном прогоне.

### 1.6. Тарифы Yandex Search API и стоимость (справочно)

Оплата — **постоплата за фактические запросы**, не подписка. Используем только
текстовые запросы в **отложенном** режиме (не генеративные ответы 5080 ₽/1000):

| Продукт | Цена / 1000 | Применение |
|---|---:|---|
| Ночные отложенные текстовые | 25,41 ₽ | основной ночной SEO-сбор |
| Дневные отложенные текстовые | 30,5 ₽ | доп. дневной API-сбор (если нужен) |
| Дневные синхронные текстовые | 488 ₽ | ручное «Проверить сейчас» (мгновенно) |

Оценка при ~40 запросах × 2-3 API-профиля: **~60-150 ₽/мес**. Боевые дневные
прогоны идут браузером и API-денег не стоят.

### 1.7. Расписание (мультизапуск)

Расписание настраивается на проект: как минимум один ночной `seo`-прогон;
опционально — дневной/вечерний `battle`-прогон (браузером) по «горячим»
коммерческим запросам. Раздел 26 исходного ТЗ (несколько раз в день) —
поддерживается.

## 2. Масштаб и единица работы

Целевой рабочий сценарий проекта:

```text
~40 запросов
5-7 сайтов
до 5 профилей
```

**Единица работы — одна выборка выдачи (`запрос × профиль`).** Все отслеживаемые
сайты матчатся по уже скачанной выдаче этого прогона, без дополнительных запросов
к Яндексу.

```text
40 запросов × 5 профилей = ~200 выборок выдачи в день
сайты (5-7)             = +0 выборок (матчатся по скачанной выдаче)
глубина ТОП-50          ≈ 5 подгрузок страниц на выборку (для браузера)
```

При таком объёме лимиты Яндекса не являются узким местом; ограничения носят
поведенческий характер (см. раздел 1.2). Тяжёлая очередь и прокси-ферма из
исходного раздела «Масштабирование» — задел на вырост, а не требование MVP.

## 3. Определение позиции (уточнено)

Позиция считается по **органической выдаче**.

Правила:

- **Колдунщики пропускаем.** Блоки Яндекс.Бизнеса, Карт, Видео, Товаров,
  Картинок, быстрых ответов и прочие вертикали **не участвуют** в нумерации
  органической позиции.
- **Реклама (Директ) пропускается** и не входит в органическую позицию.
- **Дубли домена:** если домен встречается несколько раз, берётся **лучшая
  (высшая) позиция**; остальные вхождения игнорируются.
- Если сайт не найден в пределах глубины: `position = NULL`, `status = NOT_FOUND`,
  в интерфейсе `>N`.
- Полная выдача сохраняется всегда (см. раздел 5), чтобы позицию можно было
  **пересчитать** при изменении правил.

### 3.1. Отдельный показатель — позиция в блоке Яндекс.Бизнеса

Для **локальных запросов** (например, «ресторан Екатеринбург»), где блок
Яндекс.Бизнеса доминирует, дополнительно фиксируется **позиция сайта/организации
внутри блока Бизнеса** — как **отдельная метрика**, не смешиваемая с органической
позицией.

- В `search_results` тип результата размечается через `result_type`
  (см. таксономию ниже), в т.ч. `business` для элементов блока Бизнеса.
- В таблицах и графиках органическая позиция и «позиция в Бизнесе» показываются
  раздельно.

### 3.2. Таксономия `result_type`

Минимальный набор значений, размечаемых при сохранении выдачи:

```text
organic      — обычный органический результат (участвует в позиции)
ad_top       — реклама сверху (Директ)
ad_bottom    — реклама снизу
business      — элемент блока Яндекс.Бизнеса / организаций (отдельная метрика)
maps         — блок Карт
video        — видео-колдунщик
images       — картинки
market       — товары/Маркет
fast_answer  — быстрый ответ / featured-блок
other        — прочие вертикальные блоки
```

Только `organic` участвует в расчёте органической позиции. `business` участвует в
отдельной метрике «позиция в Бизнесе».

## 4. Метрики (уточнено)

- **Средняя позиция** — `AVG(position)`, **без учёта NULL/NOT_FOUND** (не как
  ноль и не как 50).
- **Обязательно рядом со средней — coverage:** число (и доля) запросов, у которых
  вообще есть позиция в пределах глубины. Без coverage средняя обманчива: вылет
  сайта из ТОП-50 (NULL) «улучшает» среднюю, хотя фактически стало хуже.
- **Медиана** — `MEDIAN(position)`, также без NULL.
- **ТОП-3 / ТОП-10 / ТОП-20 / ТОП-50** — количество запросов с `position <= N`.
- Метрики считаются в разрезе `сайт × профиль × период`. Профили и устройства
  (mobile/desktop) **не смешиваются**.

### 4.1. «Последняя подтверждённая позиция» (формально)

Для сравнений «было → стало», страниц запроса/сайта и уведомлений базой служит
**последняя проверка со статусом `SUCCESS` или `NOT_FOUND`** для данной пары
`запрос × сайт × профиль`. Проверки со статусами `ERROR`/`BLOCKED`/`CAPTCHA`
**пропускаются** при выборе базы и **никогда** не записываются как позиция.

Сравнение периодов считается на пересечении дней, где в обоих периодах есть
подтверждённые данные.

## 5. Полное сохранение выдачи и аудит

Как в исходном ТЗ (обязательно), с уточнениями:

- Для каждого прогона сохраняется полная выдача (все результаты с `result_type`).
- Сохраняется `source` (`api`/`browser`), `search_url`/параметры запроса, версия
  парсера.
- Скриншот/HTML — только для браузерных прогонов и **опционально** (объём).
- Тяжёлые артефакты (HTML, скриншоты) хранятся в файловом хранилище/объектном
  сторидже, **не в БД**; в БД — путь/ссылка.

## 6. Схема БД (выпрямлена)

Единица работы — `check_runs` (одна выборка выдачи). `search_results` — полная
выдача прогона. `checks` — вычисленная позиция сайта в прогоне.

### projects
```text
id, name, description, active, created_at, updated_at
```

### queries
```text
id, project_id, query, group_name, priority, active, comment,
is_local (bool)            -- локальный запрос: включает трекинг блока Бизнеса
created_at, updated_at
```

### sites
```text
id, project_id, name, url, domain, active, comment,
match_mode                 -- 'domain' (вкл. поддомены) | 'exact_host'
created_at, updated_at
```

### profiles
```text
id, project_id, name, type, region, device, browser,
source                     -- 'api' | 'browser'
browser_profile_path,      -- только для source='browser'
active, settings_json,     -- секреты/cookies хранить в зашифрованном виде
created_at, updated_at
```

### check_runs  (единица работы: одна выборка выдачи)
```text
id, project_id, query_id, profile_id,
source,                    -- 'api' | 'browser'
search_url, started_at, finished_at,
status,                    -- QUEUED/RUNNING/SUCCESS/NOT_FOUND/ERROR/BLOCKED/CAPTCHA
duration_ms, error_code, error_message,
parser_version, screenshot_path (nullable), raw_html_path (nullable)
```

### search_results  (полная выдача прогона)
```text
id, check_run_id, position, url, domain, title, snippet,
result_type,               -- organic/ad_top/ad_bottom/business/maps/...
raw_data
```

### checks  (вычисленная позиция сайта в прогоне)
```text
id, check_run_id, project_id, query_id, site_id, profile_id,
checked_at,
position,                  -- органическая позиция, NULL если не найден
business_position,         -- позиция в блоке Бизнеса (nullable), для локальных
status                     -- зеркалит статус прогона
```

### position_history  (денормализованный слой для графиков/сравнений)
```text
id, project_id, query_id, site_id, profile_id, date,
position, business_position, status
```

### reports
```text
id, project_id, name, period_start, period_end, params_json,
file_path, created_by, created_at
```

### notifications
```text
id, project_id, site_id, query_id, profile_id,
type,                      -- rise/drop/left_top10/...
old_position, new_position, delta, channel, sent_at, status
```

### users  (авторизация — раздел 38 исходного ТЗ)
```text
id, login, password_hash, role,   -- Admin | Viewer
active, created_at, updated_at
```

### audit_log  (история изменений — раздел 40 исходного ТЗ)
```text
id, user_id, entity_type, entity_id, action, diff_json, created_at
```

### 6.1. Ретеншен и партиционизация

- `search_results` и `check_runs` **партиционировать по месяцам**.
- Задать политику хранения (напр., полная выдача — N месяцев, агрегаты
  `position_history` — бессрочно). Значения — параметр проекта.
- Скриншоты/HTML — отдельная политика хранения из-за объёма.

## 7. MVP (урезан) и порядок работ

**Сначала пилот** (до полной разработки): 1 профиль, ~30-40 реальных запросов,
несколько дней. Цель — измерить:

1. процент блокировок/капчи при браузерном сборе с VPS (жизнеспособность связки
   VPS + решалка капчи);
2. реальное расхождение выдачи между профилями (нужны ли все 5 или можно урезать).

**MVP (ядровой цикл):**

- 1 профиль (Desktop через API как самый надёжный старт);
- проекты, запросы, сайты, профили, БД, авторизация;
- сбор: захват **полной выдачи**, расчёт органической позиции, обработка
  ошибок без ложной позиции;
- ежедневный запуск + ручной «Проверить сейчас»;
- история позиции + один график;
- корректные статусы `SUCCESS/NOT_FOUND/ERROR/BLOCKED/CAPTCHA`.

**Следующие этапы:** остальные профили (в т.ч. браузерные персонализированные),
тепловые карты, сравнение периодов, метрики полностью, PDF/экспорт, уведомления,
роли, масштабирование (Celery+Redis вместо APScheduler при росте очереди).

## 8. Размещение и деплой

Система размещается на существующем **VPS** (`root@77.110.125.73`, хост
`magic-copper`) и обслуживается на домене **`stat.xmassage.vip`**.

По конвенциям репозитория (см. `CLAUDE.md`):

- **Запуск процессов — только через Supervisor**, не systemd. Конфиги кладутся в
  `deploy/supervisor/<имя>.conf` и копируются в `/etc/supervisor/conf.d/`.
  Отдельные программы: веб-приложение (FastAPI/ASGI, напр. под uvicorn/gunicorn),
  планировщик/воркеры сбора. После правок:
  `supervisorctl reread && supervisorctl update`, затем `restart <программа>`.
- Код живёт в `/root/<имя-папки>` (администрирование под root).
- Логи — через `stdout_logfile`/`stderr_logfile` в `/var/log/<имя>.out.log` и
  `.err.log`, не через journald.
- **nginx** как reverse-proxy перед приложением, виртуальный хост на
  `stat.xmassage.vip`, проксирование на локальный порт приложения.
- **TLS** для домена — сертификат Let's Encrypt (certbot), автопродление.
- Доступ к админке — только по HTTPS, с авторизацией (роли Admin/Viewer).
- PostgreSQL и (при переходе на Celery) Redis — локально на том же VPS.
- Браузерные profile-каталоги и `settings_json` с cookies — с ограниченным
  доступом на ФС, секреты в зашифрованном виде (раздел 38 исходного ТЗ).

Playwright/Chromium на сервере используется как для браузерного сбора
персонализированных профилей, так и (по исходному ТЗ) для генерации PDF из
HTML-шаблона.

## 9. Остаётся без изменений из исходного ТЗ

Действуют как есть: принцип «не записывать техническую ошибку как позицию»
